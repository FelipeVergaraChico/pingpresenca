# ADR 0001 — Base executável E0

Estado: adotada na E0 · 10/09/2026.

## Contexto e escopo

A E0 precisa subir a instalação, configurar fuso e criar um owner único com evidência real de concorrência. A documentação de produto permanece inalterada; esta decisão escolhe os mecanismos internos necessários. Não implementa entidades acadêmicas, convites ou chamada.

## Decisões

| Área | Escolha | Motivo e consequência |
| --- | --- | --- |
| Repositório | npm workspaces, frontend e backend independentes | Uma instalação de dependências e comandos comuns, sem framework de monorepo adicional. |
| Runtime | Linha Node.js 22, mínimo 22.12 | Ambiente local disponível e versão declarada; images/lockfile permitem reproduzir os testes. |
| HTTP | Fastify 5 e Zod 4 com objetos estritos | Esquemas explícitos rejeitam campos adicionais em vez de aceitar papéis/horários enviados pelo navegador. |
| Banco | PostgreSQL 16, `pg`, SQL parametrizado | Controle direto de transações, índices e restrições; sem ORM obrigatório para o núcleo pequeno. Cada transação usa o mesmo client, conforme [node-postgres](https://node-postgres.com/features/transactions). |
| Migrations | SQL numerado, checksum, registro e advisory lock | Execução transacional e idempotente; concorrência não aplica o schema duas vezes e alteração de arquivo já aplicado é recusada. Não há down destrutivo. |
| Bootstrap | Lock da linha singleton + índice único parcial de owner + marcador durável | Proteção transacional entre instâncias e restrição no banco. Conta, perfil, papel, marcador e auditoria são atômicos. |
| Senhas | scrypt assíncrono, salt aleatório, N=131072/r=8/p=1, hash versionado | Usa recurso do runtime com custo de memória; parâmetros ficam no backend e poderão evoluir por versão do hash. [API Node](https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback). |
| Sessões | Token aleatório, somente hash SHA-256 no PostgreSQL; cookie HttpOnly/SameSite Strict | Expiração/revogação e papel atual são consultados no servidor. Sem credencial em Zustand/localStorage. |
| CSRF e rede | Mutações JSON exigem origem exata; HTTPS/cookie Secure fora de loopback | Mesmo origin através de proxy, sem CORS permissivo ou confiança em `X-Role`/horário do cliente. |
| Limites de tentativa | Bootstrap 5/min e login 10/min por IP na E0 | Contenção inicial para a instalação de um único responsável. Rever identificação pelo proxy antes do acesso de turmas; não é política final de capacidade. |
| Tempo | `timestamptz` e relógio PostgreSQL; Temporal para conversão explícita | Auditoria e validade de sessão não dependem do navegador. Intervalos usam início inclusivo/fim exclusivo. Horários locais ambíguos/inexistentes são rejeitados. |
| Fuso da instalação | Persistido na primeira inicialização; divergência com ambiente bloqueia startup | Não reinterpretar histórico ao alterar `.env`. Interface de mudança de fuso/replanejamento fica no marco apropriado. |
| Auditoria/privacidade | Eventos append-only por API/trigger; perfil pessoal separado | Eventos iniciais guardam identificadores e mudanças mínimas, sem senha, token, segredo ou cópia do perfil. Política de retenção futura exige procedimento explícito. |
| Interface | React 19, Vite 7, Zustand 5 apenas para apresentação | Formulário real de bootstrap, login e estado inicial autenticado. Identidade visual editorial verde/papel, fontes do sistema e ausência de serviços externos de tipografia. |
| Testes | Node test runner + tsx; Vitest 4/Testing Library; PostgreSQL real; Playwright/axe | Unitários de regras, transações reais e fluxo de navegador. Mocks não substituem a prova de concorrência no banco. |

Versões exatas e dependências transitivas estão em `package-lock.json`. O Vitest inicialmente avaliado foi atualizado para a linha corrigida 4.1.11 devido ao aviso de dependência identificado durante a E0; não foi utilizado `audit fix --force`.

## Fronteiras importantes

- Login/logout e consulta protegida existem como fundação verificável de autenticação. Não há gestão de usuários, convites, recuperação de senha ou promoção de papéis na interface/API E0.
- O guard inicial tem somente `installation:read`; permissões acadêmicas futuras precisam definir recurso e vínculo, não herdar um bypass genérico de papel.
- O próprio PostgreSQL e os operadores com acesso privilegiado à infraestrutura fazem parte da fronteira confiável. O trigger não promete impedir adulteração por um superusuário do banco. A auditoria atual impede mutações silenciosas pela aplicação.
- O Compose E0 fornece um usuário de banco para instalação/migration/runtime. Separação operacional de credenciais e privilégios de migration deve ser considerada na preparação pública; nada exige essas credenciais no frontend.
- O bootstrap não grava o segredo em configuração persistente, não verifica e-mail e não é recuperação. A exclusividade de recuperar owner pela infraestrutura permanece requisito futuro, sem rota alternativa nesta entrega.
- A primeira migration é explícita. O procedimento oficial de atualização, com backup obrigatório antes de migrations sobre instalação existente, continua no escopo E6. Não há autorização para dispensar esse requisito.
- Os helpers de tempo são fundação. Não considerar atendidos cenários de matrícula, frequência ou chamada só porque usam a mesma representação temporal.

## Validação

Consulte [evidências E0](../entregas/e0.md). Os testes de integração verificam rollback da criação do owner quando a auditoria falha, disputa por duas instâncias HTTP, índice de owner, sessões, revogação e proteção do fuso persistido. O navegador verifica formulário, teclado, mobile e axe.
