## Entregue

- Configuração administrativa da duração padrão e abertura docente limitada ao horário da aula; snapshot persistido, contexto e modo fixados.
- Projeção exclusiva com QR/código rotativo, contadores, tela cheia e suspensão de códigos ao encerrar/perder sincronização, sem dados individuais.
- Login prévio, autorização curta, conta/aula visíveis e confirmação explícita antes da geolocalização.
- Aceitação, rejeição e pendência conservadoras; novas tentativas preservam histórico; resultado de transporte incerto pode ser consultado sem reenviar localização.
- Painel docente, presença manual sem tentativa prévia, decisão de pendência/correção com motivo e versão; intervenção administrativa identificada.
- Fechamento manual/automático com ausências elegíveis, preservação de pendências e auditoria transacional.
- Histórico próprio e frequência separada PILOT/OFFICIAL, após primeiro fechamento; pendências separadas e percentual nulo quando não há denominador.

Principais arquivos: `backend/migrations/003_attendance.sql`, `backend/src/attendance/{domain,service,routes,worker}.ts`, `frontend/src/attendance/`, integração em App/Workspace/OfferingPanel, testes `backend/test/{attendance.unit,e2.integration}.test.ts`, `frontend/src/attendance/Attendance.test.tsx` e `e2e/bootstrap.spec.ts`. [ADR 0003](../adr/0003-chamada-e2.md) documenta parâmetros, concorrência, privacidade e D02.

## Como experimentar sem alterar registros oficiais

1. Instale dependências com `npm ci --registry=https://registry.npmmirror.com` nesta rede. Em instalação existente, pare escritas e faça **backup antes de migrar**. Execute `npm run db:migrate` e `npm run dev` conforme README. Compose requer rebuild antes de `docker compose run --rm migrate`. O banco real não foi migrado durante o desenvolvimento desta entrega.
2. Use turma PILOT e contas sintéticas. Cadastre local verdadeiro para teste físico ou um local sintético apenas quando estiver em ambiente de teste identificado. Matrícula deve começar antes da aula. Planeje início anterior ao instante atual e término futuro, no fuso exibido.
3. Como professor vinculado, abra a aula e a chamada. Abra a projeção em outra aba/janela. Administração pode intervir, mas precisa justificar.
4. Em outra sessão, entre como aluno e use código digitável ou QR. Verifique conta/turma/aula e clique em **Confirmar minha presença**. Permita localização para caso válido; negue para demonstrar pendência. Não altere dados de uma turma oficial para simular esse fluxo.
5. No professor, selecione **Analisar**, confira a cronologia e decida com justificativa. Teste também presença manual de um aluno sem tentativa. Feche e verifique ausência de aluno elegível sem presença/pendência, auditoria e histórico próprio.
6. Uma chamada fechada não pode ser reaberta nesta entrega. Para outra demonstração, prepare uma nova aula PILOT; não apague registros para contornar essa restrição.

Em celular remoto, o QR precisa apontar para domínio acessível por HTTPS, com `PUBLIC_ORIGIN` correto e proxy configurado; `localhost` aponta para o próprio celular. A localização real do navegador exige ambiente seguro. O Compose de loopback é adequado ao teste local, não publica sozinho acesso móvel seguro.

Comandos na raiz; PostgreSQL de teste sempre em containers/volumes aleatórios descartáveis. Nenhum teste usou o banco real ou alterou `.env`.

| `PLAYWRIGHT_CHANNEL=chrome npm run test:browser` | Fluxo integrado aprovado com Chrome real, API e PostgreSQL, sessões separadas, confirmação por link QR e código, 13 verificações axe sem violações. |
| `NPM_REGISTRY=https://registry.npmmirror.com npm run test:compose` | Build Node 22, migrations 001–003, bootstrap/login e persistência após recriar containers aprovados. |

No host, os comandos usaram Node 24 e emitiram aviso de engine; a referência do projeto continua **Node 22** e o build/runtime Compose foi verificado nessa versão. O Chromium padrão do Playwright não estava instalado, por isso a execução bem-sucedida usou Chrome local. O smoke Compose passou após usar IPv4 publicado explicitamente e aguardar prontidão HTTP, não somente início do container.

O navegador exercita código digitável, projeção, geolocalização via API real com **posição emulada**, análise justificada, fechamento e frequência. Capturas em `test-results/e2-*.png` são artefatos locais regeneráveis, não prova de GPS físico ou leitura por câmera/projetor. Contraste insuficiente encontrado pelo axe foi corrigido e a suíte reexecutada. Inspeção visual da projeção também foi realizada.

## Pendências explícitas

- Verificação assistiva humana com Orca/NVDA/VoiceOver: login, código, confirmação, expiração/reinício, resultado, decisão e histórico; conferir anúncios/foco durante atualizações. Necessária para encerrar formalmente a aceitação da E2.
- Câmera lendo projeção real, GPS indoor e redes/dispositivos simultâneos são validações de piloto, não da simulação automatizada.
- Reabertura, matriz operacional completa e testes de carga são E3/E6. Nada aqui comprova 100 tentativas/s.
- SMTP, recuperação, recorrência, arquivamento/cancelamento, exclusões e consolidação inteiramente manual continuam nos marcos documentados.
- Nesta cópia, comandos Git não reconhecem um repositório; não foi possível produzir `git diff/status`. Não foi recriado `.git` nem alterado histórico.
